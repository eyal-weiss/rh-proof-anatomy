Anatomy of the claimed proof of the Riemann Hypothesis

Which parts of mathematics Levent Alpöge's Claude-assisted argument draws on, and how old each ingredient is. A crude first-order map, built from the 20-step outline in his four-page note and from a text scan of the Lean code released with it.

Read this as a map of a claim. The proof was announced on 20 November 2026 and nobody outside has checked it yet. Two kinds of numbers appear below. Importance weights are judgment calls: a first estimate from the note's outline, then a re-estimate by Claude Fable 5.2 that also read the Lean findings, with a range of several points either way. Lean weights are measured by scanning the 175,187-file Lean archive as text, without building it, through name patterns that are themselves judgment calls. A few technique identifications are guesses, marked with hollow dots.

How the Lean shares were measured, with three alternative methods as checks
  1. Every .lean file was read as text. Import lines and folder names inside qualified names were removed first; folder labels otherwise inflated some counts about sevenfold.
  2. 47 name patterns, each tied to one branch, were counted. Examples: Mathlib's Scheme and IsCMField, theta lifts, Siegel–Weil, Hecke, ℤ-lattices, Fourier and Haar, étale. A pattern's count in a file is damped to log(1 + n), so one name repeated hundreds of times cannot take over a file.
  3. Each file's code lines were split among branches in proportion to those damped counts, then summed over all files.
  4. Files with no matching name at all, 23% of the lines, take the branch mix of the other files in their folder. That is the version in the bars.
  5. Checks in the table: leaving those files out; giving each of them the mix of the files that import it, since a helper serves whatever uses it; and giving each of the 793 folders wholly to its dominant branch. All agree on the top three branches and on the near-absence of analytic number theory and combinatorics. The folder-majority method disagrees on the middle branches, so treat anything under about 7% as rough.

Infrastructure share, shown separately

This second view exists only to show how much of the code is generic infrastructure. The 23% of lines in helper files with no branch-specific name get their own bar instead of being shared out, and every percentage is of all code lines.

Read the infrastructure bar as a floor. Files that do contain branch-specific names also contain plenty of generic algebra, and this view counts that toward their branch.

Inside the Lean archive

The 14-part archive was extracted and read as text. It was not built, so nothing here checks the proof.

After comments and strings are stripped, the code contains no sorry, admit, axiom declaration, opaque, native_decide or implemented_by. That is necessary for a complete proof but does not show one: only a full build followed by #print axioms, and ideally lean4checker or comparator, can. The top file proves riemannHypothesis and four Dirichlet L-function statements, stated with Mathlib's own riemannZeta and DirichletCharacter.LFunction.

The 12 largest folders hold of the code

  • Nearly half the code (47%) sits under Development/AbelianVarietyTheory. The note's outline does not present abelian varieties as an ingredient beyond CM curves. Folder names alone mislead: IwasawaDecomposition is the Lie-group decomposition G = KAN, not Iwasawa theory. That is why the shares above come from names inside the code rather than from folders.
  • 136,003 files import all of Mathlib with a single line, so imports say little about which areas a file uses. The files that import specific Mathlib modules mostly pull in ring theory, analysis, number theory and linear algebra. Those are foundations, not the high-level branches charted here.
  • Every file is reachable by imports from the main theorem. The scan therefore cannot tell which code the final proof actually depends on; that needs a build and a declaration-level dependency trace.
  • 1,070 files sit in folders called PublishedTheorems, named after classical results such as Jacquet–Shalika, Poitou–Tate, Ferrero–Washington, Kisin and Clozel's purity. They contain 4,993 theorem declarations. Names alone cannot show whether these prove the results in full or only the cases needed.

What this map leaves out

  • The two weightings measure different things. The importance estimates weigh an idea by its role in the argument; the Lean weights measure how much code each branch takes. Foundations that Mathlib lacks, such as abelian schemes and hermitian lattices, need a great deal of code, while the RH-specific argument built on them may be short.
  • The Lean shares rest on name patterns. Some names are ambiguous: Mathlib's Lattice is an order lattice, and IsTheta is an asymptotic bound, not a theta function. A technique can also be formalized under names no pattern catches. A faded timeline row means the name is rare in the code, not that the idea is absent.
  • The importance re-estimate is an AI judgment by Claude Fable 5.2, made from the note and 15 Lean files on the main-theorem chain. It matched Lean statements to outline steps by their shape, since many names are opaque. It could not tell whether outline steps 3 to 7 survive in the final formal argument, which is the main reason for the wide range on analytic number theory.
  • The outline is a compressed sketch. The author says his summaries of Claude's parts are paraphrases that may be inaccurate.
  • Four names in the note are ambiguous. "Weyl" is read here as the character and dimension formulas, "Behrend" as the 1946 progression-free set construction, "Turán" as the power-sum method, and "Mehta" as the Mehta–Dyson integral.
  • Names that appear only as background in the note's footnotes are not plotted: Bałaban's multiscale induction, Borger's approach to the field with one element, and "Gabber's hypersurface" from one of Katz's arguments, which could not be dated.
  • Years mark the first appearance of an idea. Most of these tools kept developing for decades afterwards, and the form used in the proof is usually a later one.
